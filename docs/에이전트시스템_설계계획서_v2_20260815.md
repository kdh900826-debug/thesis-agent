## 1. 작업 컨텍스트

### 1-1. 배경

v1~v32에서 사람이 수동 반복해온 판정 절차를 에이전트화하되, v1이 남긴 두 개의 미해결 부채를 구조로 해소한다: ① 개별 종목 판정만으로는 **상관 집중 리스크를 포착할 수 없다**(액션아이템 ④), ② 섹터·매크로 재료가 개별 종목 상향 근거로 새어 들어가는 경로를 프롬프트 권고가 아니라 **컨텍스트 격리**로 막아야 한다(P6·F11).

### 1-2. 목적

| 계층 | 목적 |
|---|---|
| L1 매크로 | KC-1~9 정량 판정. 서사 없이 met / not_met / provisional만 |
| L2 종목 | 개별 기업 뉴스·공시 1차 자료 리서치 → Claim·Delta 생성 |
| L3 섹터 | 섹터 내 종목 결과 취합 → **섹터 컨센서스**(공통 축 방향 + 종목 간 분산) |
| L4 통합 | 섹터 뷰 + KC + 상관 → 포트폴리오 리밸런싱 **의견**, thesis 정교화 제안 |

### 1-3. 범위

**포함:** 1차 자료 수집·등급 판정, 사실/추론 분리, thesis Delta 매핑, 시그널 등급 후보 판정, KC 판정, 섹터 컨센서스, 구조적 상관 분석, 리밸런싱 시나리오 제시, thesis 수정 제안, 버전 발행

**제외:** 매수·매도 지시, 목표가 산출, 자동 주문, 가격 시계열 상관계수 산출, 판정의 최종 확정(사람), 매크로 전망 내러티브 생성

### 1-4. 입출력

| 구분 | 내용 |
|---|---|
| **입력** | 사용자 실행 명령 + 종목/섹터 지정 / `/config/*.yaml` (커버리지·KC·노이즈 필터·소스 등급·상관 축·포지션 비중 범위) / `/state/thesis_cards/{TICKER}.yaml` / 무료 지표 API(FRED 등)·웹·EDGAR 1차 자료 / (선택) 사용자 붙여넣기 원문 |
| **출력** | `/output/{run_id}/` 하위 단계별 JSON + 최종 `.md` 판정 패키지 + `ThesisPatch` 제안 |

### 1-5. 제약조건

1. 에이전트는 **후보 판정까지**. 시그널 확정·버전 발행 승인·포지션 행동은 사람
2. 실행 환경은 **Windows 로컬 Claude Code**(D4). `/output/`·`/state/`는 로컬 파일시스템에 영속하므로 v1 F2의 원인이었던 세션 초기화 소실은 발생하지 않는다. 대신 F2 가드는 다음으로 대체된다 — ① 발행 승인된 안정 버전은 `/docs`로 격리 ② 덮어쓰기 절대 금지(P9) ③ 주기적 백업(사용자 책임) 권장 문구를 `version-publish`가 출력
3. 규칙 파일(`/config/*.yaml`)은 **에이전트 지침에 임베드하지 않고 외부 파일로 유지** — 사용자가 직접 편집·유지보수
4. 상위 계층은 하위 계층의 **원문 컨텍스트를 상속하지 않는다**. 파일 기반 구조화 산출물만 전달
5. LLM은 판단·정성 분석·자연어 생성에만 사용. 임계 비교·집계·파일 I/O·스키마 검증은 스크립트

### 1-6. 용어

| 용어 | 정의 |
|---|---|
| **섹터 컨센서스** | 섹터 내 종목들의 Delta가 **공통 축에서 같은 방향을 가리키는 정도**. 종목 평균이 아니라 방향 일치도 + 분산 |
| **분산(divergence)** | 같은 섹터 내 종목 간 판정이 갈리는 상태. 섹터 요인이 아니라 개별 실행 요인이 지배적임을 시사 |
| **구조적 상관** | 두 종목이 **동일 드라이버 축에 노출된 정도**. 가격 상관계수가 아님 |
| **축 공유도** | 종목 쌍의 축별 노출 벡터 중첩. 상/중/하 3단으로만 표기 |
| **ThesisPatch** | thesis 카드 9항목 중 수정이 제안된 항목의 diff. 자동 반영 불가 |
| **Run** | 사용자 요청 1회로 실행되는 전체 또는 부분 파이프라인. `run_id = YYYYMMDD_HHmm` |

|---|---|---|
| **P13** | **계층 단방향 원칙.** 근거는 하위→상위로만 흐른다. 섹터 컨센서스·매크로 KC·포트폴리오 뷰는 **개별 종목 시그널의 근거가 될 수 없다.** 상위 계층의 판정이 하위 계층 산출물을 소급 수정하는 것을 금지 | `signal-arbiter` 입력 스키마 / `validate-output` |
| **P14** | **상관 표기 원칙.** 구조적 축 공유도를 상관계수처럼 소수로 표기하지 않는다. 표기는 상/중/하 + 공유 축 명시 + 근거 Claim ID. "상관 0.7" 같은 서술은 출력 거부 | `correlation-map` 스킬 |
| **P15** | **리밸런싱 의견 원칙.** L4 산출물은 **시나리오·한도·이격도**다. 목표 비중 단일값, 매수·매도 동사, 시점 지시를 생성하지 않는다 (P12의 계층 확장) | `cio-portfolio` |
| **P16** | **신선도 명시 원칙.** 온디맨드 실행이므로 모든 산출물은 `as_of` + `staleness_days`를 갖는다. 이전 Run의 캐시를 재사용한 필드는 `reused_from: run_id`를 명기하고, 유효기간 초과 시 판정은 `provisional` 강제 | `state-audit` / `kc-eval` |
| **P17** | **컨텍스트 격리 원칙.** 서브에이전트는 자신의 담당 범위 밖 원문을 컨텍스트에 로드하지 않는다. 종목 에이전트는 타 종목 원문을, 섹터 에이전트는 타 섹터 산출물을 보지 않는다. 통합은 L4에서만 | 에이전트 입력 계약 / 오케스트레이터 |

### 2-3. 자동 검출 확장

v1 §1-1의 `VALIDATE(output)`에 다음을 추가한다.

```
VALIDATE_V2(output, layer):
  # v1 승계분 전부 수행 후
  assert layer == "signal" -> 입력 Claim 중 scope != "company_specific" 인 것 == 0      # P6, P13
  assert layer == "sector" -> 개별 ticker signal 등급을 변경하는 필드 == 없음            # P13
  assert layer in {"correlation"} -> 수치형 상관계수 표기 == 0                          # P14
  assert layer == "portfolio" -> 매수/매도/목표비중 단일값 표현 == 0                    # P15
  assert 모든 산출 필드에 as_of 존재 AND (reused_from 존재 시 staleness_days 표기)      # P16
  assert layer in {"publish","thesis_patch_apply"} -> pending_approvals의 해당 건 status == "approved"  # D6, F19
  else -> REJECT(output) 후 재생성 (최대 2회) -> 실패 시 에스컬레이션
```

### 3-4. 컨텍스트 격리 강제 메커니즘 (D7 — P17·P6·P13의 실제 구현 수단)

Claude Code 서브에이전트는 프롬프트가 금지해도 파일시스템의 임의 파일을 읽을 수 있으므로, "물리적 차단"은 다음 2중 수단으로 구현한다.

| 수단 | 내용 |
|---|---|
| **① 사전 필터 스크립트 [CODE]** | 오케스트레이터가 서브에이전트 호출 **전에** 필터링된 입력 파일을 생성하고, 프롬프트에는 **그 경로만** 전달한다. 예: signal-arbiter에는 `03_input/arbiter_{t}.json`(`scope == company_specific` Claim만 남긴 필터본)을 생성해 전달 — 원문 `02_company/{t}.json`의 경로는 프롬프트에 아예 등장하지 않는다. sector 에이전트에는 해당 섹터 산출물만 모은 입력 디렉토리를 전달 |
| **② 프롬프트 화이트리스트** | 각 AGENT.md에 "로드 가능한 파일 화이트리스트"를 명시하고, 목록 외 파일 접근을 지침으로 금지 |

**한계(명시 의무):** 이 방식은 훅(PreToolUse) 수준의 하드 차단이 아니다. 에이전트가 지침을 어기고 원문 경로를 추측·탐색하는 경로는 이론상 열려 있으며, 이는 `validate-output`의 사후 검증(P13 위반 필드 검출, F13 테스트)이 최종 방어선이 된다. 훅 기반 하드 차단은 유지보수 비용 대비 이득이 확인되면 후속 버전에서 도입을 재검토한다.

### 4-2. 캐시 및 신선도 판정 (P16)

온디맨드 실행에서는 마지막 Run 이후 경과 시간이 불규칙하므로, **오케스트레이터는 모든 Run 시작 시 `state-audit`를 먼저 수행한다.**

```python
# /config/staleness.yaml (v1 §6-3 승계 + 계층 산출물 추가 + 단위 이원화 D9)
# unit: trading_days = 미국 시장 거래일 기준(주말·휴장일 미산입) / calendar_days = 달력일
STALE_LIMIT = {
  # 시장 지표 — 거래일 기준 (주말 직후 실행 시 불필요한 provisional 방지)
  "VIX":      {"limit": 2,   "unit": "trading_days"},
  "yield_30y":{"limit": 3,   "unit": "trading_days"},
  "brent":    {"limit": 3,   "unit": "trading_days"},
  "ON_RRP":   {"limit": 5,   "unit": "trading_days"},
  # 24/7 거래 지표 — 달력일 기준
  "BTC":      {"limit": 2,   "unit": "calendar_days"},
  # 저빈도 지표 — 달력일 기준
  "SDLLMTK":  {"limit": 14,  "unit": "calendar_days"},
  "FCF":      {"limit": 100, "unit": "calendar_days"},
  # 계층 산출물 — 달력일 기준 (신규)
  "ClaimSet": {"limit": 3, "unit": "calendar_days"}, "DeltaSet": {"limit": 3, "unit": "calendar_days"},
  "SignalDecision": {"limit": 5, "unit": "calendar_days"}, "SectorConsensus": {"limit": 7, "unit": "calendar_days"},
  "CorrelationView": {"limit": 30, "unit": "calendar_days"}, "ThesisCard": {"limit": 90, "unit": "calendar_days"},
  # 사용자 입력 상태 (신규)
  "Positions": {"limit": 30, "unit": "calendar_days"},        # /config/positions.yaml (D13)
  "PendingApproval": {"limit": 14, "unit": "calendar_days"}   # 승인 대기 건 유효기간 (D6)
}

for artifact in required_inputs(command):
    if not exists(artifact):        -> 선행 단계 실행 큐에 삽입
    elif age > STALE_LIMIT[type]:   -> 사용자에게 [재실행 / 캐시 사용(provisional)] 확인
    else:                           -> 재사용, reused_from = 이전 run_id 기록
```

**금지:** stale 캐시를 재사용하면서 `staleness_days`·`reused_from`을 표기하지 않는 것. `validate-output`에서 거부.

### 4-3. 상태 전이

```
IDLE
 └─(명령)→ AUDIT ──(입력 부재/stale)──→ RESOLVE ──(사용자 확인)──┐
                │                                                 │
                └─(입력 충족)─────────────────────────────────────┤
                                                                  ▼
                                                              EXECUTING
                                                                  │
                        ┌────────(검증 실패, 재시도<2)─────────────┤
```

**PENDING_APPROVAL의 영속화(D6):** 이 상태는 대화 컨텍스트가 아니라 `/state/pending_approvals.json`에 기록된다. 온디맨드 실행 특성상 승인은 며칠 뒤 다른 세션에서 일어날 수 있으며, 그때의 전이 규칙은 다음과 같다.

1. 모든 Run 시작 시 `state-audit`가 대기 건을 **최우선 보고**한다 ("승인 대기 N건: ap_...")
2. 승인 행위는 `approve <id>` / `reject <id>` 명령(또는 사용자가 큐 파일의 `status`를 직접 수정)
3. 대기 건이 `PendingApproval` staleness 한도(기본 14일)를 초과하면 `expired`로 전환 — **승인 불가, 해당 단계 재실행 요구** (근거 데이터가 낡은 상태에서의 승인 방지)
4. `approve` 없이 PUBLISHED로 전이하려는 시도는 `validate-output`이 거부한다 (F19)

| SDLLMTK (KC-6) | **API 부재** → 웹검색 | [LLM] — 동일 가드 | 사용자 수동 입력 |
| 하이퍼스케일러 FCF (KC-7) | 분기 공시(EDGAR) 기반 — 분기 1회 | [CODE]+수동 확정 | — |

## 6. 상관관계 설계 (구조적 방식)

### 6-1. 드라이버 축 정의 (`/config/correlation_matrix.yaml`)

| 축 ID | 축 | 대표 관측 지표 |
|---|---|---|
| `AI_CAPEX` | AI 인프라 CapEx 사이클 | 하이퍼스케일러 합산 CapEx·FCF(KC-7), SDLLMTK(KC-6) |
| `RATES` | 금리·조달비용 | FFR 확률(KC-1), 30Y |
| `CRYPTO` | 크립토 사이클 | BTC(KC-3) |
| `REGULATION` | 규제 확정 이벤트 | CLARITY, SEC 면제, SB6·PUCT |
| `GPU_SUPPLY` | GPU 공급·감가 | 배정 일정, 감가상각 정책 |
| `POWER_PERMIT` | 전력·인허가 | DC 모라토리엄 5단계 프레임 |
| `RISK_APPETITE` | 위험선호 | VIX(KC-2), ON RRP(KC-4) |

### 6-2. 노출 벡터 스키마

```yaml
# /config/correlation_matrix.yaml — 사용자 직접 편집 대상
IREN:
  AI_CAPEX:     {sign: "+", strength: "H", basis: ["MS $9.7B TCV", "480MW 인도 목표"]}
  CRYPTO:       {sign: "+", strength: "M", basis: ["BTC 채굴 현금흐름"]}
  RATES:        {sign: "-", strength: "M", basis: ["건설 조달"]}
  POWER_PERMIT: {sign: "-", strength: "H", basis: ["TX SB6 강제 감축"]}
CRCL:
  RATES:        {sign: "+", strength: "H", basis: ["Reserve Income = 유통량 × 이자율"]}
  REGULATION:   {sign: "+", strength: "H", basis: ["SEC 면제·CLARITY"]}
  CRYPTO:       {sign: "+", strength: "M", basis: ["USDC 유통량"]}
# ... 7종목 × 축
```

`sign`: 축이 **상승**할 때 종목에 유리(+)/불리(−) / `strength`: H·M·L / `basis`: 근거(Claim ID 또는 서술)

### 6-3. 산출물

| 산출 | 정의 | 표기 |
|---|---|---|
| **축 공유도** (쌍별) | 두 종목이 같은 축에 같은 부호로 노출된 정도. `H+H=3, H+M=2, M+M/H+L=1` 합산 후 3구간 매핑 | **상 / 중 / 하** + 공유 축 명시 (**수치 금지, P14**) |
| **역방향 노출** | 같은 축에 반대 부호 → 자연 헤지 | 축명 + 헤지 강도(상/중/하) |
| **KC 파급 시뮬** | KC 1건 트리거 시 영향 받는 종목 목록·수·합산 비중 | 예: `KC-3(BTC<55K & VIX≥25) → IREN·COIN·HOOD·CRCL 4종목` |
| **축 집중도** | 축별 포트폴리오 비중 합 — `positions.yaml`의 **비중 범위 상단** 기준 보수적 계산(D13). 임계(예 60%) 초과 시 경보 | 축별 비중표(범위 상단 기준임을 명기) + 초과 여부 |
| **섹터 간 상관** | 섹터 노출 벡터 = 섹터 내 종목 벡터의 비중 가중 합 | 섹터 쌍 공유도 + 공유 축 |

### 6-4. 이 방식의 한계 (명시 의무)

`CorrelationView` 산출물 말미에 다음을 고정 문구로 포함한다: 본 상관은 **구조적 노출 판정**이며 실제 가격 동조화를 예측하지 않는다. 축 노출이 낮아도 유동성 이벤트에서 동반 하락할 수 있다. 노출 벡터는 사람이 편집한 `correlation_matrix.yaml`에 의존하므로, **벡터의 정확성이 곧 이 레이어의 정확성 상한**이다.

## 12. 한 줄 결론

v1이 "판정 규율의 자동화"였다면 v2는 **규율을 계층 구조로 물리화하는 것**이다 — P6(섹터확신≠포지션확신)을 프롬프트 권고가 아니라 `signal-arbiter`의 입력 필터로, 매크로 서사 오염을 D3(내러티브 금지)로, thesis 자동 변조를 `requires_human_approval`로 각각 차단했으며, 온디맨드 실행 전환에 따라 **staleness 감사가 선택이 아닌 필수 선행 단계**가 되었다. v2.1 설계 인터뷰로 실행 환경(로컬 Claude Code)·지표 피드(무료 API+웹검색 이원화)·승인 게이트(영속 큐)·격리 강제(사전 필터본)·KC 지표 선택이 모두 확정되어, 남은 병목은 **§8-7 임계 수치의 사용자 확정(R2)과 상관 노출 벡터 초안(U4) 단 두 가지**다 — 이 둘이 확정되기 전에는 5종목 KC와 L4 상관 레이어가 로드되지 않는다.
